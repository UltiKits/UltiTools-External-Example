# FieldJournal 1.0.0 — Paper acceptance checklist

Use a fresh Paper 26.3 server (build 258) on Java 25 and a matching UltiTools 7.0 framework JAR. Put the framework JAR in `plugins/`. In the framework's `plugins/UltiTools/config.yml`, use `language: auto`, `fallback-language: en`, and `datasource.type: sqlite`; let the framework generate its config on a first start without the module if needed, then stop it. With the server stopped, put `target/FieldJournal-1.0.0.jar` in `plugins/UltiTools/plugins/`, start the server and keep the startup log. Do not use Bukkit `/reload`.

Use a player with `fieldjournal.use` (make the player an operator on the fresh server) and an ordinary non-operator without that permission. Start the first player in English (US). Join or reconnect both players after setting their permissions. Run the rows in order with the same first player so the counts and note below match. Command examples with `/` are for the client; omit `/` in the server console. Expected messages below give the displayed text, without colour or log prefixes.

| ID | Preconditions | Steps | Expected |
| --- | --- | --- | --- |
| Command | First player has no journal entries; second player has no permission. | As the second player, type `/fieldj` and inspect suggestions without executing. As the first player, type `/fieldjournal record r` without executing and inspect suggestions. Then send `/fieldjournal record forest`. | `/fieldjournal` is absent from the second player's suggestions. `river` is offered to the first player. Sending the command shows `Recorded forest (entries: 1).` |
| Messages | Command row passed; framework uses `language: auto`. | Run `/fieldjournal status` in English. Change the client language to 简体中文 (中国), then run `/fieldjournal status` again as the same player. Switch the client back to English. | In English: `Entries: 1; latest site: forest.` In Chinese: `累计 1 条；最近地点：森林。` |
| Dialog | Messages row passed and the client is back in English. | Run `/fieldjournal note`. Type `Blue moss` in the text box and press the save button. Open the form again, type `Unsaved note`, press **Cancel**, then run `/fieldjournal status`. | The native dialog title is `Field Journal — New note`, with `Field note` and `Save note`. Submission prints `Saved field note: Blue moss`. After cancellation, status still includes `Field note: Blue moss`. |
| Chest | Dialog row passed, with `Blue moss` saved. | Run `/fieldjournal book`. Click the writable book in the centre of the one-row chest screen. | Title: `Field Journal — Journal book`. Book name: `Read saved journal`. The chest closes and chat shows `Entries: 1; latest site: forest.` and `Field note: Blue moss`. |
| Scheduled task | Server ticking at about 20 TPS; first player in game. Config still uses the default `reminder-seconds: 60`. | Observe at least two consecutive reminder ticks in the console. Change `reminder-seconds` to `5` in `plugins/UltiTools/pluginConfig/FieldJournal/config/journal.yml` and run `/ul reload` from the console. Observe the next three tick lines and the first player's action bar. | Each tick logs `Field Journal reminder tick.` The default log spacing is about 60 seconds; after reload it is about 5 seconds (measure consecutive lines after the first post-reload tick). The player sees `Field Journal reminder: record a site or add a note.` |
| Configuration | Journal screen closed; file generated in the previous row. | Set `journal-name: Ranger Log` in the same file. Run `/ul reload`, then open and close `/fieldjournal book`. Set `journal-name: '   '` and run `/ul reload` again; reopen the book. Restore `journal-name: Ranger Log` in the file and reload before moving on. | The book title changes from `Field Journal — Journal book` to `Ranger Log — Journal book`. The blank value is refused (the console contains `Module 'FieldJournal' failed to reload:` and `journalName`), and the book still opens as `Ranger Log — Journal book`. |
| Data | Same first player with one recorded site and `Blue moss` saved; SQLite backend selected. | Send `/fieldjournal record river` and `/fieldjournal status`. Stop the server normally; with it stopped, use SQLite in read-only mode to inspect the module DB (example below). Start it again and run `/fieldjournal status` as the same player. | Before stop: `Recorded river (entries: 2).`, `Entries: 2; latest site: river.` and `Field note: Blue moss`. Table `field_journal_entries` contains one row with `2`, `river`, `Blue moss`. After restart, the same two status lines appear without recording again. |
| Bootstrap | Startup log retained; an operator in survival has an empty inventory slot. | Look for the module's declaration in the startup log before enable. Use `give <player> minecraft:diamond_shovel` in the console. Have the player hold the shovel and run `enchant <player> fieldjournal:trail_mark 1` from the console. Inspect the shovel's tooltip. | The bootstrap logger prints `Declared Trail Mark (fieldjournal:trail_mark).` The held shovel gains an enchantment named `Trail Mark`; a successful declaration log alone does not pass this row. |

Example read-only table check, from the stopped server's directory (requires the `sqlite3` CLI):

```bash
sqlite3 -readonly plugins/UltiTools/sqliteDB/FieldJournal.db \
  'SELECT entry_count, site, note FROM field_journal_entries;'
```

Expected output on this fresh setup: `2|river|Blue moss`.
